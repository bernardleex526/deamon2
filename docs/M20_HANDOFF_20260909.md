## 1. 当前结论

当前版本应视为：**最小 M20 适配 + 已复现失效保护修复，尚未完成实机跟随验收**。

- 上游跟随主体保留：目标质心、目标关联窗口、可选卡尔曼、前后距离控制、偏航控制、走廊/APF。
- 已保留的 M20 适配：`/LIDAR/POINTS` 到 `/m20/scan`、ROS 传感器 QoS、M20 坐标方向参数、`basic_server` UDP `Type=2 Command=25`、BasicStatus 门控、超时和停止保护。
- 已修复：走廊左右边界初始化/边界选择问题；空扫描现在清除缓存并立即发布零速度。
- 已移除：实验性的 target-directed holonomic 斜向平移策略及 `holonomic_follow` 配置。
- 当前策略是上游风格：目标偏角使用 `angular.z` 转向；前向距离使用 `linear.x`；不保证严格“原地转完再前进”，也不主动将目标角度分解成 `linear.y`。
- 现场此前看到的横向异常尚未宣称完全解决；必须用真实 bag 和 GOS dry-run 复核。

## 4. 数据来源和坐标

M20Pro 是 AOS/NOS/GOS 多主机架构。官方雷达是前后两枚；当前 GOS 数据链路使用厂商合并输出：

```text
前雷达 + 后雷达
 -> NOS/厂商雷达链路和组播
 -> GOS 厂商解码
 -> /LIDAR/POINTS (PointCloud2)
 -> pointcloud_to_laserscan
 -> /m20/scan
 -> robot_nexus
```

现场配置 `send_separately: false`，所以 `/LIDAR/POINTS` 是前后雷达融合点云；不能把它解释为只有前雷达。后方数据对跟踪目标可以被空间过滤，但完整门控不应因跟踪只看前方而丢掉后方保护。

官方资料给出前雷达相对 body：`x=+320.28 mm, y=0, z=-13 mm`；后雷达：`x=-320.28 mm, y=0, z=-13 mm`。厂商合并点云已经做过坐标转换，当前 `config/m20.yaml` 的 `target_frame: ''` 是故意避免二次 TF 变换。头部 frame 当前按 `lidar_link` 检查；若现场固件实际是 `base_link`，先确认点坐标已是 body 坐标再改标签检查，不能额外重复平移。

验证发布者和数据，不能只看 publisher count 或驱动日志：

```bash
ros2 topic info -v /LIDAR/POINTS
ros2 topic hz /LIDAR/POINTS
ros2 run jie_deamon m20_cloud_probe.py --seconds 12 --cloud-only
```

通过条件：非零点数、时间戳新鲜、约 10 Hz、`usable_fresh_samples=true`。

## 5. 关键 ROS 话题和服务

| 名称 | 类型/作用 |
|---|---|
| `/LIDAR/POINTS` | `sensor_msgs/msg/PointCloud2`，当前前后融合点云 |
| `/m20/scan` | `sensor_msgs/msg/LaserScan`，跟踪输入 |
| `/m20/cmd_vel_raw` | `geometry_msgs/msg/Twist`，算法意图，不是实测速度 |
| `/m20/cmd_vel_guarded` | `geometry_msgs/msg/Twist`，Guard 输出，不是实测速度 |
| `/m20/bridge_status` | `std_msgs/msg/String`，dry-run/armed/reason/velocity |
| `/robot_nexus/target` | `geometry_msgs/msg/Point`，手动目标种子/调试入口 |
| `/robot_nexus/set_moving` | `std_srvs/srv/SetBool`，只开关算法跟随计算，不等于 AOS arm |
| `/m20/arm` | `std_srvs/srv/SetBool`，Guard arm；live 前必须另做控制权验收 |

当前 launch 明确关闭 Web、Android、actions。不要用旧 Web 页面绕过门控。

## 6. M20 控制协议边界

官方文档规定速度轴：body X 正为前进、Y 正为左移、Yaw 正为逆时针。ROS `/NAV_CMD` 是 `drdds/msg/NavCmd`，只在导航模式有效；当前实现选择 basic_server UDP 速度接口，使用物理单位 `Type=2, Command=25`，不是归一化的 `Command=21`。

当前 bridge 每 50 ms 处理一次，并通过同一 UDP socket 每秒发送心跳以注册状态；收到完整 BasicStatus 才可能 arm。核心条件包括：`MotionState=17`（RL 控制）、导航使用模式、非充电、非急停、非休眠、支持步态、扫描新鲜且无停止区障碍。超过输入、扫描、状态或命令超时必须归零并解除 arm。

官方文档同时警告 `/NAV_CMD`/速度输出可能与 NOS `planner` 以及 `charge_manager` 冲突。实机前必须确认原厂规划、回充和充电任务空闲并明确唯一速度控制权；不得只看到 ROS 话题就开始运动。

轮足平台的步态有效范围（文档 V1.1.7+）：

```text
0x1001 标准基础：X >= 0.20, Y >= 0.35, |Yaw| >= 0.50（非零区间）
0x1003 标准楼梯：X >= 0.15, Y >= 0.30, |Yaw| >= 0.40
0x3002 敏捷平地：X >= 0.15, Y >= 0.25, |Yaw| >= 0.35
```

当前 bridge 上限是 X/Y `0.30 m/s`、Yaw `0.60 rad/s`，因此基础步态的横移最低值不会被当前上限放行。必须核实实际步态后再测试；不要为通过测试擅自提高保护上限。

## 9. 真实 bag 回放和对比

回放器不启动 ROS 算法节点、不发布 ROS 控制话题、不打开 UDP；它把扫描逐帧通过 C++ `LidarTracker`。当前可运行最小修复版：

```bash
source /opt/ros/humble/setup.bash
cmake -S /home/lee/deamon2 -B /tmp/deamon2-follow-build \
  -DBUILD_TESTING=ON -DPython3_EXECUTABLE=/usr/bin/python3
cmake --build /tmp/deamon2-follow-build \
  --target m20_scan_replay test_m20_tracker -j2
python3 /home/lee/deamon2/scripts/m20_real_scan_replay.py \
  work/real-bag-replay-154448/scans.jsonl \
  --tracker /tmp/deamon2-follow-build/m20_scan_replay \
  --target 2 0 \
  --output work/real-bag-replay-154448/front-seed
```

如需严格对比上游，先准备归一化的上游头文件并编译 `m20_scan_replay_upstream`；归一化仅统一几何参数和扫描轴方向，不修改上游算法：

```bash
python3 scripts/m20_prepare_upstream_replay.py \
  /tmp/jie-deamon-upstream-20260909-review \
  /tmp/m20-upstream-normalized
cmake -S . -B /tmp/deamon2-follow-build -DBUILD_TESTING=ON \
  -DM20_UPSTREAM_INCLUDE=/tmp/m20-upstream-normalized
cmake --build /tmp/deamon2-follow-build --target \
  m20_scan_replay m20_scan_replay_upstream -j2
```

使用同一份 `scans.jsonl`、同一目标初值、同一 follow distance、同一保护参数。输出 `comparison.png`、`scan_snapshots.png`、CSV 和 JSON。结果必须分别报告 raw 与 guarded；Guarded 全零可能只是近障/未 arm，并非跟踪算法没有输出。

已观察的 bag 事实：本机最小修复版 `raw_y` 范围约 `-0.193~+0.197 m/s`，上游约 `-0.783~+0.800 m/s`；两者均有 872/1002 帧被停止区判定为障碍。这个结果支持“走廊边界修复降低横向异常”，但不证明人被正确识别，也不证明可实机行走。

## 10. 后续算法测试顺序

1. 对同一 bag 标注动作时间和目标位置，确认目标簇不是墙、机身或静态背景。
2. 比较上游与最小修复版的目标质心、目标点数、走廊项、APF 项、raw X/Y/Yaw。
3. 重点看正前方目标是否只转向/前进，左右目标是否方向符号合理，目标丢失是否归零。
4. 对近障簇做物理来源确认；不能缩小保护区来消除报错。
5. 在 GOS Foxy 编译并实时 `dry_run=true` 重测；不得覆盖运行中的已有实例。
6. 确认 NOS planner/localPlanner、充电和回充任务空闲，确认 AOS RL 状态、步态和硬急停。
7. 实机只做有人监护的低速单轴测试：先转向、再前进、再按官方允许范围测试横移；每次保留遥控/硬急停和通信断开验证。
8. 实机通过后再做手机页面；手机必须调用同一个门控和状态接口，不能绕过 `basic_server` 或控制权。

## 11. 禁止事项

- 不要设置 `commissioned=true` 作为“测试一下”的方式。
- 不要向未知 AOS 接口发送 `cmd_vel`、`/NAV_CMD` 或 UDP 速度包。
- 不要同时运行第二套 `jie_deamon`、第二个点云转换器或自建雷达接收器。
- 不要启动 `drmap mapping` 来解决跟随数据问题；建图仍由 NOS 原厂负责。
- 不要在真实 ROS Domain 播放合成点云或 bag。
- 不要把 `raw`、Guard 预览、ACK 或进程存在当成实际运动证据。
- 不要删除用户已有改动或用 force push 覆盖远端；提交前先审阅 Git diff。
